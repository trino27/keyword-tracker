# Where a document goes

`SKILL.md` next to this file is *how to write* a document. This one is *where to put it*, and it
answers the question in the order you actually have it: *I have a fact — where does it live?*

It is a contract, not advice. Nothing checks it mechanically, so a reviewer holds a `.md` that
lands somewhere this file does not describe.

---

## 1. The decision — read it top to bottom, stop at the first match

A fact goes to the **lowest** level that can hold it. If it fits two levels, it belongs to the
lower one, and the higher one gets a pointer — never a restatement.

| The fact is about… | It goes in | Example |
| --- | --- | --- |
| one line of code — why THIS, when something else was obvious | an **inline comment** | `createdBy is intentionally preserved on cancel` |
| one module: its invariants, prohibitions, public surface | `<module>/<NAME>_MODULE.md` | `crawl/CRAWL_MODULE.md` |
| one module's statuses, transitions, emitted events | `<module>/<NAME>_LIFECYCLE.md` | `crawl/CRAWL_LIFECYCLE.md` |
| one module's stable rationale — why this shape, what was rejected | `<module>/<NAME>_ARCHITECTURE.md` | `auth/AUTH_ARCHITECTURE.md` |
| a convention spanning modules of ONE workspace | `<ws>/skills/<topic>/SKILL.md` | `be/skills/performance-patterns/` |
| a convention spanning workspaces | `skills/<topic>/SKILL.md` | `skills/fe-be-roundtrip/` |
| a convention belonging to a PLATFORM, not to one service | `practices/<platform>/[<tech>/]<topic>/SKILL.md` | `practices/be/drizzle/database-patterns/` |
| a load-bearing sub-rule of a skill, too long to inline | `<skill>/rules/<name>.md` | `practices/ops/devops/rules/` |
| a long example or background for a skill, NOT read first | `<skill>/references/<name>.md` | `<skill>/references/` |
| a second contract owned by one skill, not a sub-rule | `skills/<topic>/<NAME>.md` | this file |
| the architectural vector of a whole workspace | `<ws>/ARCHITECTURE.md` | — |
| how an agent must execute a role | `.claude/agents/<agent>.md` | `.claude/agents/qa.md` |
| a slash command and workflow body written by `openspec init` — the TOOL owns both, regenerated by its own init, never hand-edited | `.claude/commands/opsx/<workflow>.md` + `.claude/skills/openspec-<workflow>/SKILL.md` | `openspec/README.md` |
| routing: which workspace, which entry point | `AGENTS.md` — hand-written and canonical. Root `CLAUDE.md` mirrors it; `<ws>/CLAUDE.md` is a one-line stub pointing at its sibling `AGENTS.md` | — |
| **an APPROVED requirement of one capability** | `openspec/specs/<path>/spec.md` — the path mirrors what it specifies; the `[<CAP>-<NNN>]` id does not contain it | `openspec/README.md` |
| **a proposed CHANGE to the requirements** | `openspec/changes/<name>/` — FLAT, never mirrored; only its delta at `specs/<path>/spec.md` mirrors | `openspec/README.md` |
| a human-facing orientation: how to run this | the root `README.md` | — |
| obsolete history kept only for traceability | `<anywhere>/archive/` | — |

## 2. The tests that decide the hard cases

**Can a script derive it?** Then do not write it by hand. Class lists, route tables, event names,
file trees, counts — a hand-written copy drifts from the code it restates, and the reader gets
the same facts faster and more accurately from source.

**Does it constrain, or does it describe?** A prohibition, an invariant, "why not the obvious
thing" — documentation. What a service is called, what the call order is, which files exist —
code. Reading code answers questions about mechanics reliably and questions about intent poorly;
documentation is the reverse, so spend it on intent.

**Who owns it already?** If any file states this fact, you are not writing it — you are either
extending the owner or adding a pointer. A partial second copy is the most expensive defect in a
knowledge base: a reader who finds it stops there and invents the rest.

**Would a human open this directory?** Then a `README.md` is right (§4). If only an agent routed
here would, it is an `AGENTS.md` or a `SKILL.md`.

**Is it a requirement or a skill?** A STATE of the system that could be wrong, and that a test
can pin (→ a requirement in `openspec/specs/`); a way of doing something well (→ a skill). A
prohibition worth enforcing becomes an ESLint rule or a test and is named in the skill beside it;
without an enforcer it is enforced by review, and the skill says so.

## 3. Rules that follow from the table

- **A `*_MODULE.md` never restates what the code lists.** It owns intent, prohibitions and
  invariants. If you are typing a file tree or a class list into one, stop.
- **An invariant names the test that pins it.** A file pointer says where to look; only a test
  fails when the doc and the code stop agreeing. No test → say `not pinned by a test`.
- **`rules/` and `references/` are different.** `rules/` is load-bearing and read when the topic
  comes up. `references/` is background, deliberately not read first. Putting a rule in
  `references/` hides it; putting an example in `rules/` inflates every read of the skill.
- **A workspace has no `docs/` of its own.** Workspace-level material is `<ws>/ARCHITECTURE.md`,
  `<ws>/AGENTS.md`, or a skill under `<ws>/skills/`.
- **No `.md` inside `src/` except the module docs** (`_MODULE`, `_LIFECYCLE`,
  `_ARCHITECTURE`). A rules file next to a component is a
  skill that has not been filed yet.
- **An execution plan lives in `docs/_plans/` and nowhere else** — its contract is
  [`docs/_plans/README.md`](../../docs/_plans/README.md). The work order within one requirement
  delta is that OpenSpec change's `tasks.md`. A finished plan is archived, never left in place.
- **A checklist a reader EXECUTES is a procedure; a checklist that RECORDS what is already done
  is a plan.** Both shapes look identical. A procedure stays where it is; a list carrying
  "done" markers is a plan, wherever it happens to be sitting.

## 4. When a `README.md` is the right container

`README.md` is for a directory a **human opens directly** and needs oriented in: the repository
root, a workspace someone clones, a tool with commands to run. It is the only document type
addressed to a person arriving without a router.

It is NOT: an agent contract (`AGENTS.md`), a convention (`SKILL.md`), or module rules
(`*_MODULE.md`). If the content answers "how do I run this", it is a README. If it answers "what
am I allowed to do here", it is not.

## 5. Naming

- Module docs: `SCREAMING_SNAKE` matching the module — `CRAWL_MODULE.md`, not `Crawl.md`.
- Skills: the folder carries the topic, the file is always `SKILL.md`.
- Never invent a suffix. `*_RULES.md`, `*_GUIDE.md`, `*_NOTES.md` are not types; whatever they
  hold belongs in one of the rows above.
- **`ARCHITECTURE.md` means two different things and both are correct**, because the path
  qualifies the name. `<ws>/ARCHITECTURE.md` is a workspace vector. Inside `src/` the name must
  carry its own module prefix (`AUTH_ARCHITECTURE.md`), because there the folder is the module
  and a bare name would collide across modules.

## 5a. Paths written inside a document

A path in prose is a claim about the filesystem. Two things follow.

**Prefer relative to the document's own directory** when the file sits under it —
`constants/crawl-events.constant.ts` inside `CRAWL_MODULE.md`. It survives the module being moved.

**Do not restate a location a listing already carries.** Naming the unit beats copying a path
that will rot; paths written in prose are the claims most likely to point at a file that has
moved. Before leaving one, `ls` it.

## 6. Before you add a document at all

Most documentation work that pays is not writing a new file — it is **deleting a second copy** or
**writing the procedure nobody wrote**. If you cannot name the owner a new file would take the
fact from, it may genuinely be new. If you can, extend that owner instead.

## 7. The shape of a skills tree

§1 says which document a fact becomes. This says how the folder holding them is arranged.

A **skills tree** is `skills/` at the repository root, `<ws>/skills/` in a workspace, or
`practices/` — which holds the same artifact and differs only in what the knowledge is ABOUT.
Every tree has the same shape, so an agent that has read one can navigate all of them:

```
skills/                             or <ws>/skills/
├── AGENTS.md                       the tree's ONLY router — required
├── CLAUDE.md                       one-line stub pointing at AGENTS.md — optional
├── SKILL.md                        the tree's own entry skill — optional
└── <topic>/
    ├── SKILL.md                    required — frontmatter with `name` and `description`
    ├── rules/<name>.md             load-bearing sub-rules of THIS skill
    └── references/<name>.md        background, deliberately not read first

practices/
├── AGENTS.md                       the tree's ONLY router — required
├── <topic>/SKILL.md                a practice true of EVERY platform, so of no bucket
└── <platform>/                     be | fe | ops — a BUCKET, carries its own AGENTS.md
    └── [<tech>/]<topic>/SKILL.md   a skill, one or two levels down
```

**A bucket needs no marker.** Buckets have their own parent, so there is nothing for an
underscore prefix to disambiguate.

**The router is `AGENTS.md`, and there is exactly one per tree and one per bucket.** It indexes
every skill under it and says when to read each. A tree without one is a folder an agent has to
`ls` to navigate.

**`name:` is the skill's address, not a label.** It is the folder name. A scope the skill already
sits in may decorate it, as a prefix or a suffix — **but only where another tree holds a skill in
a folder of the same name.** `practices/be/nestjs/path-aliases/` is `be-path-aliases` because
`practices/fe/react/path-aliases/` exists; `be/skills/performance-patterns/` is `performance-patterns`,
because nothing else is. Optional decoration is not a convention — it is the absence of one, and
a reader pays for it by asking why this name has a prefix and that one does not. Anything else is
a second name for a thing that already has one, and a grep for either finds a file whose own
frontmatter disagrees with its folder.

**`rules/` and `references/` are the only sub-folders of a skill**, and §3 distinguishes them.
`<skill>/rules/` holds sub-rules of that one skill; it is load-bearing and read when the topic
comes up.

**No `README.md` at a tree root, beside a `SKILL.md`, or inside `rules/`.**
Each of those positions already has an owner — the router and the skill — so a
README there is the partial second copy §2 warns about, and it goes stale first.
